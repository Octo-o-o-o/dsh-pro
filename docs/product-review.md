# 产品评审：当前三项优先级与历史记录

> 实施更新（2026-10-25）：用户随后授权实施以下三项，并追加本机 DSH 客户端响应式验证。三项实施与初次验收见 [实施验收记录](validation/three-priorities-2026-10-25.md)；后续独立复核、修复、172 项回归和发布状态见 [发布验收记录](validation/release-0.3.2-2026-10-25.md)。以下研究结论保留当时上下文。

> 最新增量结论：2026-10-25。用户要求保持“小而美”，只选最值得做的 3 件事，先不改产品代码。
> 本轮网页 Pro 未完成新提交：Oracle 遇 Cloudflare；内置浏览器停在验证页；本机 Chrome 可登录，但 Pro 选择器显示已达使用上限。按用户追加授权，改由两个 subagent 分别独立核对 Research、Design，再由主宿主裁决。**以下是代码核实后的替代研究结论，不冒充本轮 Pro 评估，也不是产品验收。**

## 当前只做这三件事

**先让“完成”可信，再让 Research 的交付稿跟上新证据，最后把 Design 的“选一张继续改”做顺。** 已有多轮、材料扫描、逐条判据、裁决失败交接、交付稿入口、画廊、参考图和 ZIP 足够构成基础，无需再次包装为新增功能。

### 1. 共同：让“完成”的判定和实际证据一致

用户收益：看到完成时，知道哪些要求已满足、哪些仍需自己判断；宿主也不会把自动结束误认成人工验收。

**当前证据：** [裁决解析](../packages/research/src/plugin.ts#L301)的提示词要求全部判据为 `met`，但代码 `done` 只检查 `accepted + done=true`；[引擎](../packages/core/src/engine.ts#L822)直接据此结束任务。本轮在内存调用当前原函数，确认判据含 `partial`、`unknown` 或缺失时都可能保留 `done=true`。此外，[裁决输入](../packages/research/src/plugin.ts#L431)只有本轮问题、判据和答复前 30,000 字符，没有图片；[唤醒动作](../packages/research/src/plugin.ts#L1068)也会把自动完成主题交给固定的“用户已接受”提示。这些属于程序/文案一致性问题，不是模型能力不足。

**最小范围：** 对照原成功判据检查返回项完整、无重复且全部满足，才允许自动认定判据通过；缺项或矛盾复用现有裁决重试/待判断出口，保留答复，不因此再发一轮研究或生图。合法的 `partial + done=false` 仍按原有轮次预算处理。Design 的图像质量保持人工确认。自动完成与人工接受使用各自准确的提示，继续沿用现有状态与操作。

**演示与完成条件：**

- 三条判据有一条 `unknown`，即便模型输出 `accepted + done=true`，仍进入待判断，回答和产物可读。
- 文本裁决通过不被表述为图片视觉验收；人工接受仍可作为明确的独立决定。
- 仅自动完成后唤醒宿主，不出现“用户已验收”的断言；缺项、重复项和判据不匹配有针对性回归。

投入：低至中。**不做**视觉裁决模型、置信分数、审批系统或新一套状态机。这里保证流程与证据一致，不保证研究结论客观正确。

### 2. Research：交付稿清楚标明覆盖到哪一轮

用户收益：补充材料后，能够立刻分清眼前是旧结论，还是已经纳入新证据的结论，并顺手查看对应轮次。

**当前证据：** [后端](../packages/research/src/plugin.ts#L857)仅按 `report.md` 是否存在返回路径；[概览](../packages/research/client/panel.tsx#L705)始终优先该文件，而且旧版本提示只对非 report 生效。[续轮与重做](../packages/core/src/engine.ts#L362)没有交付稿归属或过期处理。因此旧稿可能持续占据“宿主交付稿”位置；这是静态路径推导，本轮未在真实主题中重现。阅读器还刻意让链接保持纯文本，不能直接把任意 Markdown 链接全部激活。

**最小范围：** 为宿主交付稿记录所属版本、覆盖轮次和内容更新时间；续轮/重做时显示“交付稿待更新”，旧稿保留可读，旧格式显示“覆盖范围未确认”。更新文件后面板能够刷新。来源回查仅复用现有“查看本轮回答/裁决”入口；重要结论注明来源轮次即可，不建立引用管理系统，也不新增自动写报告的模型调用。

**演示与完成条件：**

- 第 1 轮建议 A并写交付稿，第 2 轮加入新证据时，旧稿立即被标注待更新，不再默认为当前完整结论。
- 新交付稿注明覆盖至第 2 轮，能够打开该轮回答/裁决；文件原地更新后可见新内容。
- 无归属信息的旧稿不会被猜成最新版；回查沿用现有文件访问边界，原始 HTML 和危险 URI 保持不可执行。

投入：低至中。**不做**知识库、通用引用系统、完整版本审批、全历史自动综合或自动事实核查。报告内容由宿主核实，“文件是新的”不等于结论正确。

### 3. Design：在画廊里“以这张继续改”

用户收益：选中自己喜欢的方向，直接表达保留什么、只改什么，得到一张可对照的改稿，不必先理解材料路径。

**当前证据：** [图片卡](../packages/research/client/panel.tsx#L753)只有预览；[续轮弹窗](../packages/research/client/panel.tsx#L1040)已有文字反馈、方向数和材料路径，但没有所选图片身份。[API](../packages/transport/src/openai-images.ts#L356)已支持从本轮文件走参考图编辑，因此不是“缺少参考图功能”，而是缺少从当前画廊到下一轮的明确衔接。普通 `regenerate` 的默认文案还偏向不同新方向，不适合作为这条微调路径的默认语义。

**最小范围：** 图片增加一个“以这张继续改”入口，打开现有 `continue` 弹窗，带入选定图片和反馈，默认本轮一个结果；记录源轮次与产物，复用既有材料校验与传输。旧图保留，通过现有查看器依次查看底图与新图，不新增并排对照面板。这个新入口只处理一张明确底图，普通多方向探索保持原用法。

**演示与完成条件：**

- 三张方案中选第 2 张，要求“保留布局，只换背景色”；记录与实际发出的材料均明确指向第 2 张，而非依赖“上一张”的口头上下文。
- 项目存储与本机存储都能把该主题产物作为底图；无效或不属于该主题的路径在发送前拒绝。
- 默认只追加一轮、一个方向；旧图不覆盖，可依来源关系回看。API 不支持 edits 或 `imageEdit=off` 时明确阻止该定向修改入口，不能悄悄退化为无底图生成。验收区分“底图确实发送”和“生成结果符合修改意图”，后者人工确认，不承诺像素级保留。

投入：中。**不做**画布、图层、遮罩编辑、素材库、批量变体、自动选优或视觉打分。

## 为什么后置其他候选

- **采用某版/某图：** 现有 `accept` 已能接受任务结果。先解决当前报告归属和定向迭代；独立的采用状态、撤销采用和导出绑定会扩大数据模型，暂不进入前三。
- **漂亮的单文件 HTML 导出：** 已有本地文件、demo 和逐轮 ZIP。先保证交出去的内容对应正确轮次，再改包装；当前不加格式矩阵或云分享。
- **大规模真实验收工程：** 真实验证必须做，但收进上述改动的交付条件，不重新开启旧六场景计划。候选版至少完成一条 Research 新证据续轮、一条 Design 指定底图修改，并验证中断后不会重复发送；如正式发布，再按既有发布流程验证实际安装版本。
- **更多模型/通道、第三次面板重设计、公共 SDK：** 对当前三处体验没有直接增益。

## 本轮验证与裁决边界

主宿主重跑 4 个现有测试文件，**56 项通过**（engine、document、continue-route、openai-images）；另对当前 `parseJudge` 原函数做内存调用，3 个矛盾输入仍返回 `done=true`，控制例 `verdict=partial` 则返回 false。测试通过不代表上述缺口已修复。未修改产品源码或测试，未重跑产品真实网页/生图 API，未构建、提交、推送或发布。

两个子任务先各自读源码，再返回意见；Design 子任务原将真实闭环验证列第三，收到可复现的判定缺口后将其提升并把验证降为交付条件。主宿主采纳共同的三项，调整为上述执行顺序；不把“安全回查”扩成任意链接支持，不把“底图发送”当成视觉质量通过。

过程材料保留在本地研究目录；原始会话、浏览器状态与恢复记录不随发布提交。

## 一句话

0.3.2 的功能密度已经够了。接下来不是加第六个功能，而是把五个接缝焊死：**版本、首跑、交付、异常、续轮**。把“能跑”变成“敢推荐”。

真正的护城河不是浏览器自动化——DOM 会改版、会风控；护城河是**记录、状态机和项目内的可交接性**。所以下面五项全部投向“证据与交接”，不投向“更多通道、更多模型、更多页面”。

## 为什么现在不该扩功能

三个断点，按伤害排序：

1. **用户看到的版本、装到的版本、验证过的版本对不上。** 源码 0.3.2 未同步；公开仓库 0.3.1；市场条目仍指 0.3.0；npm 是 0.2.x。两个 README 却把 dsh.pub 写成推荐入口。新用户还没装，就要先做版本考古。
2. **“任务完成”和“拿到能用的东西”之间还隔着一层。** `final.md` 被明确写成“机械汇总，不是交付物”，真正的稿子要宿主另写；面板却把它摆在“研究文档”的位置。Design 的文本裁决看不到图片，却可能替“方向可区分、标题可读”这类视觉判据盖章。
3. **长任务的异常证据不够。** 单轮、附件、两轮续跑有记录；真实断线、超长回答、升级迁移、真实生图 API 都还没有绑定到具体版本的验收。用户不知道“它上次失败是它的问题，还是网页的问题”。

## 五项，按用户价值 / 实现成本排序

成本是单人粗估，不是排期承诺。

### 1. 发布完整性：让“装的”等于“写的”（P0，0.5–1 天）

**症状**：四层版本并存；README 的安装命令指向一个还没有当前能力的包；验证记录混着 rc.2 与 rc.3、旧 commit 与当前 HEAD。

**改法**：

- 把 0.3.2（或直接 0.3.3）走完 `sync-dist` → 两个公开仓库 → `v<version>` tag；市场能提就提，提不了不让它阻塞主路径。
- README 主入口改成“**已验证的完整 SHA** + 对应 DSH 版本 + 日期”；dsh.pub 标“待收录”，npm 标“旧版 0.2.x”，不要让三条命令看起来等价。
- 新增 `CHANGELOG.md`：每个版本一行，写清版本、日期、DSH 版本、验证类型（单测 / 本机加载 / 真实网页 / 真实 API）。
- 修掉 5 处会改变用户行为的文档冲突（见“现场证据 → 文档漂移”）。
- 公开仓库卸载说明统一：`~/.dsh/pro-research/` 只在“两个插件都不再使用”时删除；Research 现在写的是无条件删除。

**验收信号**：

- 干净 DSH profile 按 README 第一条命令安装，装出来的版本与 README 描述一致。
- 0.3.1 的旧主题升级到候选版后，主题、轮次、本地产物仍可读。
- 验证记录都能回答：哪个 commit、哪个 DSH 版本、哪个平台、哪类证据。
- 有一条可执行的包回退方法，不要求用户自己猜。

**性质**：加深。不做新功能，只把“可信”补上。

### 2. 第一次成功不需要准备材料（P0，约 1 天）

**症状**：Research 的快速开始让用户先准备 `docs/market-notes.md`（仓库里没有这个文件），默认还跑 3 轮；Design 默认 2 轮 × 3 方向。两个 README 的首图都是空面板——用户先看到安装成本、账号风险和 ToS 警告，还没看到值得付出的结果。

**改法**：

- **首图换真实成果**：Research 用一张完成主题的概览（总结正文 + 判据 + 产物入口）；Design 用 3 张图和可打开的 demo。空态图移到“安装验证”一节。
- 两个 README 的第一个示例改成 **1 轮、0 材料、可直接复制**：
  - Research：给两个简短方案，要一张取舍表、推荐理由、一个未决问题。
  - Design · web：一张首屏图 + 一个带按钮交互的单文件 HTML。
  - Design · API：一张图，并明确写“此通道不产出 HTML”。
- 仓库放 `examples/`：一份脱敏的 `report.md`、一张 design board 截图或 HTML。用户不安装也能看到成品长什么样。
- 空态不再只说“用 `/pro-research` 开始”，而是给可复制的请求 + “成功后结果会出现在这里” + **诚实的等待预期**（Pro 网页一轮通常不是几十秒，不承诺“60 秒”）。

**验收信号**：

- 新人不需要创建任何示例文件，就能跑完第一次。
- 找 1–2 个没装过的人，只看 README 能完成首跑；记录卡点，不追求“3 人可用性实验”的仪式感。
- 看完首屏 30 秒，能说清：输入什么、拿到什么、什么时候需要自己介入。

**性质**：加深。不加向导、不加路由、不加安装状态机。

### 3. 让“完成”有交付含义（P1，1–2 天）

**症状**：状态显示完成，用户仍不知道这份东西能不能直接用；机械汇总占着“文档”的位置；判据是否满足只有一个 `accepted / partial / rejected` 标签，没有逐条依据。

**改法**：

- 面板里把 `final.md` 的正名改成“**运行汇总（自动生成）**”，不再叫“研究文档/最终文档”。
- 新增宿主交付稿契约 `report.md`，写进两个 SKILL 和 `continue/accept` 的交接提示：
  1. 当前结论与适用条件；
  2. 成功判据逐条：met / partial / unmet / unknown + 对应轮次证据；
  3. 未决问题；
  4. 产物与轮次入口。
- 面板概览优先展示 `report.md`；没有时明确显示“宿主尚未整理交付稿”，而不是拿 `final.md` 顶上。
- 裁决结果增加**逐条判据数组**（criterion / status / evidence），`done` 只在全部 met 时为 true；存进 `verdict`，面板渲染成表。
- **裁决失败不能等于任务失败**：no-JSON 时先重试一次严格 JSON；仍失败就保留答复、写 `partial + judge_error`，交宿主/人工复核。绝不把已经取回的 19KB 答案标成 `failed`。
- Design 每轮显示管线状态：“取回 2/3 图；HTML 未取回；视觉待人工确认”。API 通道直接标“图片通道”，文本裁决不得替视觉判据盖章。

**可选加分项（后置，不算第六件事）**：一键导出单文件 HTML——Research 是带判据表和轮次引用的报告，Design 是带提示词和 demo 链接的设计板，图片内嵌。用于发给别人看，不做服务器、不做协作。

**验收信号**：

- 一个真实两轮主题里，用户不读全部轮次就能找到结论、未决项和依据。
- 每个“满足判据”都能回到轮次或材料；没有依据时显示“证据不足”。
- `final.md` 存在不再被理解成“交付完成”。
- Design 缺 HTML 时不会显示“设计交付已就绪”；API 出图不会自动证明视觉判据成立。

**性质**：加深，而且是产品灵魂。如果只做一件事，做这件。

### 4. 真实异常验收与能照着做的恢复说明（P1，2–3 天）

**症状**：0.3.2 修过恢复、并发、CSP、ZIP 限额，但真实验收仍集中在“顺利路径”。一旦断线、重启、超长回答，用户只能从状态码猜。

**改法**：只建一组小矩阵，绑定拟发布的确切版本，live / fixture 分开标注：

| 场景 | 通过信号 |
|---|---|
| 真实单轮 + 同主题续一轮 | 材料、回答、裁决、轮次、面板互相对应；续轮不串到别的回答 |
| Design 真实网页图 + HTML | 图片可解码；真正下载的 HTML 能在面板和本地打开，约定交互可用 |
| 发送后中断、重启 | 已提交的远端消息不因恢复再次发送；无法自证时停在人工核对 |
| 真实长回答 | 本地取回与页面末段、关键结构一致；没有把半截当完整 |
| 一个固定 API 端点 | 生成、参考图、下载落盘、请求次数可核对；不由此推导“所有兼容服务可用” |
| 0.3.1 升级到候选版 | 旧主题可读；旧回答不会因恢复再次发到网页 |

- 恢复提示统一三段：**为什么停 / 已经保留什么 / 下一步会发生什么**。例如 API 在途请求因重启丢失：旧请求无法接管、已有图片仍在、重发会产生新请求。
- 把本次现场的两个缺陷变成回归：自动裁决失败、中文标题目录名退化（见下）。

**验收信号**：没读源码的人，仅凭提示能处理登录失效、提交未知、API 中断；失败不会被写成成功。

**性质**：加深。不是“再堆测试总数”，是把关键长尾变成有名字、有证据的场景。

### 5. 续轮 / 重做弹窗的材料入口（P2，1–2 天）

**症状**：第一次能出东西，第二次想补一份证据或品牌参考图，却要退出面板重新组织工具调用。`plan.md` 已经承认：工具侧 `regenerate materials` 修了，面板的材料选择 UI 没做。

**改法**：在现有“继续一轮 / 重新生成”弹窗里加：

- 相对主题项目根的文件路径输入；
- 本轮准备发送的材料清单、数量、错误；
- 无效路径、超限、密钥扫描命中在发送前就给明确反馈；
- 复用已有的扫描、限额、manifest 规则，不新建上传组件。

**验收信号**：Research 从面板补证据，下一轮 manifest 对得上；Design 补参考图，下一轮真的走 edits；用户能分清“本轮新增了什么”，而不是以为历史材料全部重发。

**性质**：加深。跨平台文件选择器、拖拽、素材库都不做。

## 两个插件分别怎么判断

| 维度 | Pro Research | Image Design |
|---|---|---|
| 最值得继续投入的价值 | 项目材料 → 按判据续问 → 宿主交付与交接 | 参考与反馈 → 图片 → HTML/图片产物 → 同主题继续 |
| 最值得展示的“哇点” | 加入新证据后，结论如何变化，哪些旧判断被保留或推翻 | 一个主题里看到图、打开真实 demo、再继续改 |
| 当前最弱的一环 | 机械汇总与正式交付之间的理解断层 | 0.3.2 的真实图 + HTML 端到端证据没重跑；API 承诺容易越界 |
| 应独立实现 | 判据摘要、结论格式、宿主交付要求 | 图/HTML 完整性、参考图续轮、视觉待确认提示、API 请求说明 |
| 结论 | 继续投入，定位收紧到“项目内研究与复核” | 继续投入，优先做强网页闭环；API 保持附属图片通道 |

**共享核心继续共享**：状态机、材料、回执、记录、安全边界、产物读取、基础面板壳都是同一类问题；拆两套只会把恢复和一致性缺陷维护两遍。

**但不要共享业务结论**：Research 的文本裁决不能当 Design 的视觉验收；API 的“请求不可接管”不能套用网页恢复话术。可以共享材料弹窗，不能共享一份含糊的“成功”定义。

## 明确不做 / 砍掉

1. **不做第三轮面板重设计。** 正文优先、当前版本归属、更多菜单、响应式、异步防覆盖都已有实施记录；再换一套卡片和主题，投入产出很低。9 条路由、15 个 action 是实现合同，不是卖点；不要为了数字好看盲删恢复动作，但也不要拿它当宣传。
2. **不扩 API 兼容范围，不加视觉裁决模型。** 真实服务商验收还没完成，“任意 OpenAI 兼容”已经比证据走得远。先坐实一个明确端点，按实际参数契约陈述支持范围；多账号、多 profile、多 provider、验证码绕过、通用聊天 UI 继续是非目标。
3. **不为架构整洁启动新一轮基础设施工程。** 不抽公共 SDK，不重造 worker/调度，不做覆盖全部 0.1 历史记录的迁移器。先证明“公开版能升到候选版、失败时能正确停下”。

另外两条口径：不把“单会话复用”宣传成永久记忆；不把 fixture 通过写成页面改版已兼容。

| 顺序 | 内容 | 产出 |
|---|---|---|
| 第 1–2 天 | 第 1 项：发版 + 文档冲突收口 + CHANGELOG | 一条可信的安装路径 |
| 第 3–4 天 | 第 2 项：真实首图 + 1 轮 0 材料示例 + `examples/` | 第一次成功不需要准备 |

如果时间只够两项：**1 + 3**。1 决定别人敢不敢装，3 决定装完觉不觉得值。

## 现场证据（本次调研实际跑出来的）

### 证据 A：自动裁决把已经完成的轮次判成 `failed`

- 2026-10-25 09:50 发起，09:57:50 取回 19,557 字节完整答复；09:57:51 主题变 `failed`，`stopReason: "judge returned no JSON object"`。
- 现场：`docs/research/0-3-2/events.ndjson`；原文：`~/.dsh/chatgpt-pro-research/raw/topic-0b5b55b095/01-answer.md`。
- 原因：`parseJudge()` 找不到 JSON 就抛错，`adjudicate()` 的异常走到 `handleFailure`，主题直接失败；没有重试、没有“保留答复交人工”的降级。
- 影响：用户看到的是“失败”，实际成果完好；侧边栏只剩恢复/取消，没有“让宿主裁决”的出口。
- 修法：第 3 项。先重试一次严格 JSON；仍失败写 `partial + judge_error`，保持主题可恢复，并通知宿主裁决。

### 证据 B：中文标题的目录名退化成 `0-3-2`

- 标题“两个插件的小而美产品补强评审（0.3.2 之后）”生成的目录是 `docs/research/0-3-2`。
- 原因：`slugifyTitle()` 把所有非字母数字替换成 `-`，只要还剩 ASCII 就直接用；没有检查它是不是只剩数字/版本号。
- 影响：记录目录不可读、容易和 `dsh-pro-0-3-2` 这类真实版本目录混淆；不同标题可能撞名。
- 修法：ASCII 结果里至少要有足够字母（或长度 ≥ 6）才采用，否则回退 `topic-<hash4>`；补一个中文 + 版本号的测试。

### 证据 C：文档漂移（会改变用户行为）

| 位置 | 现在的写法 | 实际 / 冲突 |
|---|---|---|
| `packages/research/README.md`（已知限制） | “重要结论建议 `human_check`” | `human_check` 是提交核对（submitted / not_submitted / reopen），不是内容质量验收 |
| `docs/usage.md`（设置表） | `judgeProvider` 留空“跑满轮次” | README 与代码都是“留空用 DSH 默认模型自动裁决”；本次还因此失败 |
| `packages/design/README.md`（首图说明） | 用 `/gpt-image-design` 开始 | 实际技能名是 `pro-design`（`docs/usage.md`、`resources/skills/pro-design`） |
| `packages/design/README.md`（开头） | 网页/API 与“图片 + HTML demo”连写 | 后文明确 API 只出图片；首句应先区分通道 |
| `packages/research/resources/skills/pro-research/SKILL.md` | “同一主题始终续原会话” | 后文允许会话丢失后生成 `context.md` 重开；应写成“可用时续用，丢失后显式重建” |

另有两处证据归属需要收紧，但不算功能缺陷：兼容表写 rc.3 实测，公开安装记录是 rc.2；根 README 汇总结论时没有把每条验证绑定到具体分发 commit。

## 对 Pro 建议的裁决

- **采纳**：五项主线、排序、两个插件分别结论、共享核心、三条“不做”、差异化定位（卖项目交接，不卖“也能调研”）。
- **部分采纳**：
  - “找 3 名未参与开发的 DSH 用户”成本过高；改为 1–2 名真实新人走一遍 README，记录卡点即可。
  - 第 4 项 2–4 人日作为“每次发版的门槛”太重；改成一张 6 场景矩阵，其中 3 条 live、3 条 fixture，绑定版本，按季度补，不阻塞小版本。
- **驳回**：
  - “根 README 的‘Design 完成 7 图 + demo’与 fixture 记录矛盾”——不成立。`docs/design/dsh-pro-website` 是真实的 `web-pro` 主题：3 轮、7 张图、`code-01.html`。fixture 只用于面板精修。该驳回不改变“每条验证要绑定 commit/产物”的结论。
  - “API 与网页混成同一承诺”是文档首句的问题，不是功能设计问题；后文和代码已经区分，按第 1 项改文案即可。
- **补充**（Pro 没展开、我认为更关键）：
  - 自动裁决失败必须是“交接”，不能是“失败”（证据 A）。
  - 记录目录名是产品的一部分，不是实现细节（证据 B）。
  - 不要承诺“60 秒首跑”；Pro 网页一轮的等待不可控，承诺时长会制造新的失望。改为“不需要准备材料 + 诚实等待预期”。

## 一句话定位

> 它不跟官方 Deep Research 比“生成一份报告”，而是把 ChatGPT Pro 网页会话变成 DSH 项目里的可审计任务：材料、轮次、判据、产物都留在项目里，停了能接，结论由宿主裁决。

用户选它的理由不是“也能调研”，而是：**订阅额度直接用、产物进项目、失败能停住、下一次能接着改。**
